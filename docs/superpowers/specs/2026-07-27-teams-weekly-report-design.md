# 既卒生 メモリア週次レポート → Teams 自動送信 設計

作成日: 2026-07-27

## 目的

2026年度既卒生（国家試験対策対象者24名）のメモリア実施状況を、毎週月曜の朝に
担当教員の Teams チャットへ自動で届ける。教員が「今週誰に声をかけるか」を
1通のメッセージで判断できる状態にする。

## 前提と制約（調査で確定した事実）

- 対象者は `/Users/ny/Documents/2026既卒生国家試験対策進捗状況一覧20260604.xlsx` の24名。
  同ファイルは 2026-06-04 時点のスナップショットであり、氏名と分類（①〜⑥）しか持たない。
  学籍番号を持たないため、**このファイル自体をシステムのデータソースにはしない**。
- 学生名簿スプレッドシート（ScriptProperty `STUDENT_LIST_ID`）の `students` シートに
  `student_number` / `student_name` / `department` / `grade` があり、24名は登録済み。
  ただし `grade=4` だけでは他の学生と区別できず（入学年違いの既卒生も混在）、
  **「今回の対象24名」を示す情報が存在しない**。
- **大半の対象者はまだメモリアを実施しておらず、`student_logs` に1行も存在しない。**
  したがって「誰が未着手か」はログから導出できない。対象者名簿を明示的に持つことが必須。
- 学習ログは `student_logs` に蓄積され、`ArchiveService` が古い分を
  `student_logs_YYYY-MM` シートへ退避する。累計値の算出はアーカイブも走査する必要がある。
- 既存の `automation/parent-report/ParentReport.gs` が、既卒生の月次集計 →
  Gemini 文面生成 → Power Automate 送信という近い処理を実装済み。集計部分の考え方を踏襲する。

## 決定事項

| 論点 | 決定 | 理由 |
|---|---|---|
| 送信経路 | Power Automate（HTTP要求トリガー）→ チャットに投稿 | 個人チャットへのDMが可能。保護者レポートと運用系統が揃う |
| 送信タイミング | 毎週月曜 7:00 JST（先週月〜日を集計） | 週の頭にその週のフォロー対象が確定する |
| 未着手者の表示 | 全員の氏名を列挙（経過週数つき） | 24名なら1通で全体像が読める。放置が長い順に声をかけられる |
| 分類①〜⑥・月次目標 | **レポートには使わない** | 教員の手元管理に留める。仕様変動をシステムに持ち込まない |
| AI 文面生成 | **行わない** | 事実の集計のみ。追加課金ゼロ、氏名を外部APIに送らない |

## アーキテクチャ

```
[students シート]           [student_logs / student_logs_YYYY-MM]
  report_group='2026既卒'            回答ログ
        │                                │
        └────────┬───────────────────────┘
                 ▼
   TeamsWeeklyReport.gs（週次トリガー 月 7:00）
                 ├─ 集計・状態判定
                 ├─→ 週次Teams_YYYYMMDD シート（記録・検証用）
                 └─→ POST JSON → Power Automate → Teams チャット（担当教員）
```

### 構成要素

**1. 対象者定義 — `students` シートの `report_group` 列（新規追加）**

対象24名の行に `2026既卒` と入力する。対象の増減はこの列の編集のみで完結し、
コード変更を伴わない。値は文字列で、将来 `2027既卒` などを並行運用できる。

- 責務: 「誰にレポートするか」の唯一の正本
- インターフェース: `student_number` をキーに `student_name` と `report_group` を返す
- 依存: なし（教員が手で編集する）

**2. 集計・送信 GAS — `automation/teams-weekly/TeamsWeeklyReport.gs`**

問題バンクスプレッドシートの Apps Script プロジェクトに配置する。

- 責務: 週次の集計、シートへの記録、Power Automate への送信
- 主要関数:
  - `buildAndSendWeeklyReport()` — トリガーから呼ばれる本体
  - `buildWeeklyReport(dryRun)` — 集計してシート出力まで。`dryRun=true` なら送信しない
  - `collectWeeklyStats_(ss, from, to)` — 対象者ごとの集計（下記データ構造を返す）
  - `formatMessage_(stats, from, to)` — 送信ペイロードの組み立て
  - `postToTeams_(payload)` — UrlFetchApp による POST とエラー処理
  - `installWeeklyTrigger()` — 初回に一度だけ手動実行
- 依存: `students` シート、`student_logs`（＋アーカイブ）、ScriptProperties

**3. 送信先 — Power Automate フロー**

「HTTP 要求の受信時」トリガー → 「チャットまたはチャネルにメッセージを投稿」
（投稿者: フロー ボット、投稿先: 担当教員とのチャット）。
フロー URL は ScriptProperty `TEAMS_FLOW_URL` に保存し、**リポジトリには置かない**。
URL 自体が共有秘密であり、CLAUDE.md の secret 判定基準に該当する。

## データフロー

1. トリガー起動（月曜 7:00）
2. `students` から `report_group='2026既卒'` の行を取得 → 対象 `student_number` 集合
3. `student_logs` および `student_logs_YYYY_MM` アーカイブシートを2パスで走査する
   - パス1: `student_number` が対象集合に含まれる行から `student_id`（UUID）を収集し、
     学生ごとの UUID 集合を作る
   - パス2: `student_number` が対象、**または** `student_id` が収集済み UUID に一致する
     行を集計対象とする

   **`student_number` 単独で突合してはならない。** PWA の単問回答 API
   （`submitAnswer`）は `studentNumber` を送らず、`AnswerService` は
   `student_number: studentNumber || ''` と空文字で書き込む。学籍番号だけで突合すると、
   実際に学習している学生が「未着手」として報告される。
   また `updateStudentNumber` は live シートしか書き換えないため、学籍番号が変わった
   学生はアーカイブ分の履歴を失い、`firstDate` が今週に見えて
   「🌱今週はじめて着手」と誤表示される。UUID 突合はこの両方を防ぐ。

   補助的に `profile` シート（`student_id` と `student_number` を両方持つ）からも
   対応を取り込む。ただし同シートは教員が手で保守するもので空のこともあるため、
   欠損は異常ではなく通常の no-op として扱う。

   **`profile` シートへの信頼について（意識的な判断）**: `ProspectiveService.getMyProfile` は
   同じシートを「`student_id` と `student_number` の両方が一致して初めて信頼する」
   （なりすまし防止）という方針で使っている。本レポートはこれと逆に、
   学籍番号だけを手がかりに UUID を取り込む。これは認証ではなく集計であり
   被害範囲が違うため許容するが、前提として明記しておく。

   誤りが混入する経路は限定的である。打ち間違いの UUID は実在しないため無害
   （どのログ行にも一致しない）。実害が出るのは profile シートで
   コピペミスや1列だけのソートが起き、学籍番号と UUID の対応が総崩れになった場合のみ。
   その場合でも、学籍番号が入っているログ行は直接突合が優先されるため、
   誤帰属しうるのは「学籍番号が空の行」＝もともと紐づけ不能として数えている層に限られる。

   **この対策で塞がる範囲（正確に）**: 単問回答 API `submitAnswer` は export されているが
   呼び出し元がなく、実際の回答はすべてバッチ経路（`syncPendingAnswers`）を通る。
   バッチはプロフィールの学籍番号を毎回同じ値で送るため、学生は「全行に学籍番号がある」か
   「全行にない」かのどちらかになる。したがって UUID 突合が救えるのは
   **学籍番号未設定のまま学習し、後から設定した学生**である。

   **残る穴**: 学籍番号を一度も設定していない学生は、データからは
   「未学習」と区別できない。これはデータ上どうやっても解けない。運用で
   「未着手」に見える学生に連絡する際は、プロフィール設定漏れの可能性を先に疑うこと。

   どの UUID にも紐づけられなかったログ行数（`student_number` 空かつ UUID 未解決）は
   Logger に記録するのみとし、**監査シートにも Teams メッセージにも出さない**。
   全校規模の数字であり、教員には解釈も対処もできないうえ、自分の担当学生の
   欠落と誤読される危険がある。

4. 学生ごとに集計:
   - 今週（月00:00〜日23:59:59 JST）の回答数・学習日数・正答率
   - 累計回答数・最終学習日・初回学習日
5. 状態を4分類に判定:

   | 状態 | 条件 |
   |---|---|
   | 今週実施 | 今週の回答数 ≥ 1 |
   | 今週はじめて着手 | 今週実施 かつ 初回学習日が今週内 |
   | 停止中 | 今週の回答数 = 0 かつ 累計 ≥ 1 かつ 最終学習日から14日以上経過 |
   | 未着手 | 累計回答数 = 0 |

   （今週未実施だが最終学習日から14日未満の学生は「今週実施」にも「停止中」にも
   該当しないため、`小休止（N日前に学習）` として停止中セクションの下に短く出す）

6. `週次Teams_YYYYMMDD` シートへ全対象者の集計結果を書き出す
7. 送信済みフラグを確認し、未送信ならペイロードを POST
8. POST 成功 → 送信済みフラグを立てる／失敗 → `ADMIN_EMAIL` へエラーメール

### 通知の優先度

`notifyAdmin_` は数が増えるほど価値が下がる。毎週必ず届く通知があると、担当者は
`[メモリア週次]` というタイトル自体を無視するようになり、本当に重要な
「レポートが届かなかった」というウォッチドッグ通知まで一緒に埋もれる。

したがってメール通知は「起きたら対処が必要で、かつ常態ではない」事象に限る。

| 事象 | 通知 | 理由 |
|---|---|---|
| ログシートが列不足で集計から除外された | **メール** | 1か月分の履歴が丸ごと欠落し、長期利用者が「今週はじめて着手」と誤表示されうる |
| 対象者0名 / 名簿シート・列の欠落 | **メール** | 設定ミス。放置すると毎週無言で失敗する |
| Teams 送信失敗 | **メール** | 手動送信が必要 |
| 週次実行の成功記録が今週ない | **メール**（火曜 8:00） | 沈黙と正常の区別 |
| `enrolled_students` が空 | **メール**（dryRun 時を除く） | 未着手週数が全員同じ値になり、順序が無意味になる |
| 紐づけ不能ログ行数 | Logger のみ | 常に非ゼロ。対処不能な全校規模の数字 |

### 未着手者の経過週数

「登録からどれだけ未着手か」の起点は次の順で決める:

1. `enrolled_students` シートに当該 `student_number` の `created_at` があればその日付
2. なければ ScriptProperty `PROGRAM_START_DATE`（既定値 `2026-05-01`＝事前アンケート開始月）

未着手者はこの経過週数の降順（放置が長い順）で並べる。

## メッセージ形式

```
📊 メモリア週次レポート  7/20(月)〜7/26(日)
対象 24名 ／ 今週実施 3名 ／ 累計未着手 19名

✅ 今週実施（3名）
  山田 太郎   42問・4日・正答率58%
  佐藤 花子     18問・2日・正答率44%
  鈴木 一郎    7問・1日  🌱今週はじめて着手

😴 停止中（14日以上・2名）
  田中 二郎   最終 7/2（24日前）・累計112問
  高橋 三郎   最終 6/28（28日前）・累計 35問

⛔ 未着手（19名／未着手期間の長い順）
  伊藤 四郎（12週）  渡辺 五郎（12週）  小林 六郎（11週）…

▶ 詳細シート: <スプレッドシートURL>
```

「小休止」該当者がいる週は、停止中セクションの直後に
`💤 小休止（1名）  加藤 七海  最終 7/24（3日前）` の形式で1行ずつ足す。

該当者ゼロのセクションは見出しごと省略する。全員未着手の週も
「今週実施 0名」を明示して送信する（送らないと故障と区別できないため）。

## エラー処理

| 事象 | 挙動 |
|---|---|
| `TEAMS_FLOW_URL` 未設定 | シート出力のみ行い、`ADMIN_EMAIL` へ「未設定のため未送信」を通知 |
| POST が非2xx／例外 | 最大3回リトライ（指数バックオフ）。全滅で `ADMIN_EMAIL` へエラーメール。シートは残る |
| `report_group` 該当者ゼロ | 送信せず、管理者へ「対象者未設定」を通知（無言で成功扱いにしない） |
| 同一週の再実行 | 送信済みフラグにより二重送信しない。シートは上書き更新 |
| `students` シート／列が見つからない | 例外を投げて停止し、管理者へ通知 |
| 実行が6分制限で強制終了 | **catch できない**。トリガーは沈黙し、Teams にも何も届かない。 |

### 沈黙を成功と区別する（ウォッチドッグ）

Apps Script の6分制限による強制終了は `try/catch` で捕捉できない。教員から見ると
「報告することがなかった週」と「壊れている週」が区別できず、これは
このシステムで最も危険な失敗である。

対策として実行開始・正常終了のタイムスタンプを ScriptProperties に記録し、
**火曜 8:00 に別トリガー**（`checkWeeklyRunHealth`）で「今週の正常終了記録があるか」を
確認して、なければ管理者へメールする。沈黙を成功の合図にしない。

あわせて走査コストを下げる。ログシートは全学科600名分が蓄積する一方、
本レポートが必要とするのは24名分・4列（`student_id` / `student_number` /
`is_correct` / `timestamp`）だけなので、`getDataRange()` で全12列を読まず
必要列のみ読む。

### 同時実行

`buildWeeklyReport` 全体を `LockService` のスクリプトロックで囲み、送信済み判定は
集計前（先頭）で行う。教員の「届いたか確認しよう」という手動実行がトリガーと
重なると二重投稿になるため。`postToTeams_` のリトライは非冪等なので、
ペイロードに `range.start` を冪等キーとして含め、Flow 側で重複排除する。

## テスト方針

GAS のためユニットテスト基盤がない。以下の手順で検証する。

1. `buildWeeklyReport(true)`（dryRun）を実行 → `週次Teams_YYYYMMDD` シートの内容を
   スプレッドシート上の実データと突き合わせて手検証する
2. 状態判定は、ログを持つ学生・持たない学生・14日以上前に止まった学生が
   それぞれ意図した区分に入ることを実データで確認する
3. `TEAMS_FLOW_URL` を設定し単発送信 → Teams チャットでの表示崩れを確認
4. 二重送信ガードの確認（同じ週にもう一度実行しても届かないこと）
5. `installWeeklyTrigger()` を実行し、翌週の自動配信を実地で確認する

いずれも「実行して結果を目視した」時点で検証済みとし、それ以前に動作を断定しない。

## 導入手順（運用者の作業）

1. `students` シートに `report_group` 列を追加し、対象24名に `2026既卒` を入力
   （xlsx の氏名と `students` の突き合わせ候補一覧は実装時に生成する）
2. Power Automate でフローを作成（手順書を実装時に同梱）
3. Apps Script に `TeamsWeeklyReport.gs` を貼り付け、ScriptProperties に
   `TEAMS_FLOW_URL` / `ADMIN_EMAIL` を設定
4. `buildWeeklyReport(true)` で dryRun → 内容確認
5. `installWeeklyTrigger()` を実行

## スコープ外（YAGNI）

- 分類①〜⑥および月次目標の達成判定
- 正答率・苦手分野の詳細分析（実施者が増えた段階で別途追加する）
- AI による文面生成
- 学生本人への通知、教員からの返信受付
- 他学科・在校生への展開

## 導入時の前提条件（見落とすと静かに壊れる）

- **Apps Script プロジェクトのタイムゾーンを `Asia/Tokyo` にする。** 週次トリガーの
  `atHour(7)` はプロジェクトのタイムゾーンで解釈される。JST でない場合、日曜のうちに
  発火して「先週」の定義が1週ずれ、しかも送信済みキーも変わるため二重に配信される。
- **氏名を含むシートは全て名簿スプレッドシート（`STUDENT_LIST_ID`）に置く。**
  対象は `students`（`report_group` 列）・`対象者リスト`・監査シート `週次Teams_YYYYMMDD` の3つ。
  問題バンクは Web アプリを `ANYONE_ANONYMOUS` で公開しているため、個人が特定できる
  データを置かない。問題バンク側に残るのは `student_logs` / `enrolled_students` /
  `profile` など、既にそこにあるものだけとする。
- **専用の Apps Script プロジェクトに置く（gas-backend に同居させない）。**
  `LockService.getScriptLock()` はプロジェクト単位である。`AnswerService.submitAnswer` は
  回答1件ごとにこのロックを取るため、gas-backend に同居させると、週次レポートが集計中
  （数分）のあいだ**全学生の回答送信がロックタイムアウトで失敗する**。月曜7時は
  利用が少ないだけでゼロではない。
- **貼り付け先プロジェクトの関数名衝突を確認する。** Apps Script は全 `.gs` が同一の
  グローバルスコープを共有するため、`prop_` / `headerIndex_` / `notifyAdmin_` などが
  既存スクリプトと衝突すると後勝ちで静かに上書きされる。

同じカテゴリ集計ロジックを流用し、二重メンテを避ける。
